# 03 統合検証と対象環境への適用を完了する

状態：完了（2026-10-17）。クラウドのプロジェクト `Meelyze-plus`（本番兼用）へ利用者の承認後に5件を適用し、読取専用チェックと `verify.sql`（ロールバック）で検証した。データをコミットする試験（並行実行・SDK経由の保存・実Storage操作・バケット設定不一致での停止）は、本番兼用のためローカル開発環境で実施した。結果・残作業は [README](../README.md) に記録した。依存：[01](01_p0_database.md)・[02](02_accounts_history.md)、[00の利用者側準備](00_user_setup.md)。

## 目的・参照

DBを再現でき、競合時もデータ・権限・公開条件を守れることを検証する。対象環境への適用結果と残るAPI側の作業を記録して、Supabase担当の構築完了を判定する。変更先は `supabase/` 配下のみ。

- [開発・検証](../../docs/development.md#検証)：DB、認証・公開範囲の検証項目。
- [DB仕様](../../docs/database.md)：保存・公開・読み取り範囲・Storage・権限の正本。
- [API仕様](../../docs/api.md)：RPCの呼び出し契約、本人履歴と公開集計の区別。
- [Supabase README](../README.md)：適用手順と適用済みマイグレーションの扱い。

## 成果物

- `supabase/tests/verify.sql`：全体の制約・原子性・権限・公開条件の検証を完成させる。最後にロールバックする。
- `supabase/tests/`：複数DB接続による競合検証、Supabase SDKのRPC・Storage操作を再現するために必要な最小限のスクリプト・依存定義。実行時の依存バージョンを固定する。
- `supabase/README.md`：実行コマンド、対象環境、ツール版、適用済みファイル、結果、未検証事項、APIへの引継ぎを集約する。別の報告用Markdownは増やさない。

## 作業・完了条件

「並行実行と原子性」と、Storageの書込を伴う項目はローカル開発環境（Supabase CLI 2.121.0）で確認した。適用先では書込を伴わない確認だけを行った。

### 再現性と権限

- [x] 空の開発DBへ5つのマイグレーションをファイル名順で適用し、11テーブル・RPC4つ・公開ビュー3つ・固定マスタ29＋4件・非公開バケットを確認する。P0段階からの追加適用でも同じ結果になる。
- [x] 同じ環境で2回目の `db push` に適用対象がないことを確認する。テーブル・索引・制約・関数のシグネチャと権限を正本と照合する。
- [x] `verify.sql` が意図しない例外や期待値不一致で失敗し、検証データを残さないことを確認する。結果を表示するだけで成功扱いにしない。
- [x] 管理者接続だけでなく `service_role` 相当でRPC・行ロック・更新拒否を確認する。`anon`・`authenticated` の読取・書込・RPC実行が拒否され、ビュー／関数／列権限にも抜けがないことを確認する。

### 並行実行と原子性

- [x] 複数接続から同じメニューへ異なる確認を同時送信し、確認が5件を超えず、失敗した確認の回答が部分保存されないことを確認する。
- [x] 同一 `request_id`・同内容の同時送信は1確認だけとなり、再送で同じIDが返ることを確認する。同IDで異なる内容・店員同意は競合になることも確認する。
- [x] 両本人設定の置換RPCをそれぞれ同一アカウントへ同時実行し、結果がどちらか一方の完全な集合となることを確認する。削除だけ・混合状態・重複を残さない。
- [x] 解析保存・確認保存・本人設定置換で途中失敗を発生させ、全体のロールバックを確認する。単一接続の検証を並行実行の確認で代用しない。

複数接続・SDKの検証は専用の開発環境で行う。コミットが必要な試験は `verify.sql` のロールバックでは掃除できないため、試験用環境の破棄または試験データだけの後始末を手順化する。

### Supabase・Storage・読み取り範囲

- [x] Supabase SDKから最終シグネチャのRPC4つを呼び、引数名・戻り値・SQLSTATEを確認する。APIサーバーを実装せず、検証コードは `supabase/tests/` に置く。
- [x] 実際のSupabase Storageで、サーバー用鍵によるアップロード・取得・削除を確認する。非公開画像を匿名・通常の認証利用者が取得できず、公開確認を作っても画像が公開されないことを確認する。
- [x] 容量上限・MIME制限、既存バケットの設定不一致時の停止を確認する。停止の検証は使い捨ての開発環境で行う。画像の画素数・実形式検証はAPI側に残す。
- [x] 画像をStorage APIで削除しても、メニュー・料理・回答が残り、本人履歴用SQLで取得できることを確認する。期限切れの解析トークンでも履歴データは残り、確認追加は拒否されることを確認する。
- [x] 同じ店舗・料理キーの複数利用者データを用意し、公開ビューは双方同意の回答だけ、本人履歴用SQLはその所有者・対象メニューだけ、内部予測用の取得は非公開を含む対象範囲になることを確認する。別店舗・別料理・別項目・店舗未選択の回答を予測対象に混ぜない。
- [x] 公開ビューに画像パス・トークンハッシュ・所有者・本人設定がないことを確認する。ビュー内の結合用IDはDB仕様どおり保持し、HTTP応答での除外・全利用者集計はAPI側の担当として引き継ぐ。

### 適用と引継ぎ

- [x] 00で指定された開発プロジェクトを、用意されたCLI認証で参照する。リポジトリ直下で `supabase link --project-ref <project-ref>` を実行し、接続先が指定と一致することを確認する。CLI管理用認証・DBパスワード・SDK用Secret Keyを混同しない。[CLIのリンク手順](https://supabase.com/docs/reference/cli/supabase-link)
- [x] 適用先のプロジェクト・環境種別・既存テーブル・マイグレーション履歴を確認する。既存の同名テーブルがあれば初回DDLを上書き適用せず、移行差分を整理する。
- [x] 開発検証後に対象環境と適用する具体的差分を提示する。[開発ルール](../../CLAUDE.md) と [適用手順](../README.md#適用手順) に従い、本番へのSQL実行・既存テーブル削除は対象と変更内容の確認を得てから行う。
- [x] 承認が必要な適用は承認後に実施し、対象環境で構成・権限・固定マスタ・Storage設定を再確認する。破壊的な試験や開発用データの投入を本番で行わない。
- [x] READMEに実行日・環境・CLI／DB／SDK版・実行コマンド・成功／失敗・未実施を記録する。秘密鍵・接続パスワード・トークン・画像・個人情報は記録しない。接続できない環境の適用・検証は未完のまま残す。
- [x] 開発中の24時間経過画像の手動削除手順を残す。一般公開前の定期削除、履歴保持期間、同意撤回・アカウント削除は未決事項として引き継ぎ、このタスクで仕様を追加しない。
- [x] API側へ、RPC契約・エラー対応・トークン検証・所有者条件・公開集計・Storage保存後のDB失敗時の画像削除を引き継ぐ。未実装のAPIやアプリ全体を完了扱いにしない。

対象環境への適用と上記検証が完了した時点でDB構築完了とする。タスク作成、SQL作成、ローカル検証、対象環境への適用はそれぞれ区別して報告する。
