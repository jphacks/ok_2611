3. 各READMEに記載した依存を追加し、動作確認したバージョンをロックファイルに固定する。
4. 各アプリの `.env.example` を作り、`.env` へコピーする。APIはPydantic Settingsで明示的に読む。秘密値をGitへ含めず、公開される `EXPO_PUBLIC_` には秘密値を置かない。
5. P0を実装・検証した後、P1を追加する。アカウントと地図がなくてもゲストでP0を一巡できるようにする。

## デプロイと運用

- フロントのRoot Directoryは `apps/mobile`、Expoは `web.output: "single"`。画面仕様の各ルートへ直接アクセスできるSPAリライトを用意する。
- APIのRoot Directoryは `apps/api`、エントリポイントは `app/main.py` の `app`。リポジトリ直下の `contracts/`・`prompts/` がデプロイに含まれることを確認する。
- フロントURLを `ALLOWED_ORIGINS`、APIの `/api/v1` を含むURLを `EXPO_PUBLIC_API_BASE_URL` に設定する。本番・スマートフォンでの確認はHTTPSを使う。
- `/api/v1/health` と `/places/select`・`/capture/preview` の直接アクセスを確認する。画面状態がない場合は店舗選択・撮影へ案内し、デプロイ保護で停止しないことを確かめる。
- Vercel Functionsのリクエスト・レスポンス本文上限4.5MBに収める。画像の2 MiB上限に加え、multipartの付加情報も含めて確認する。[Vercelの制限](https://vercel.com/docs/functions/limitations)
- レート制限は複数インスタンスで共有できる保存先を使う。プロセス内カウンターだけには依存しない。
- 解析POSTは自動再送しない。確認保存で結果が不明な場合は、同じ内容・`request_id` で再送する。
- 画像・Authorization・トークン・座標・メール・パスワード・個人の設定をログに残さない。解析・確認・アカウント・公開集計のレスポンスは `Cache-Control: no-store`。
- Supabaseは `Meelyze-plus`（Project Ref `pqegjvcyfnmqpmwxaogp`、`ap-southeast-1`）を**本番兼用**で使う。DB変更は [Supabase README の適用手順](../supabase/README.md#適用手順クラウド) に従い、対象と差分を提示して承認を得てから `db push` する。データを書き込む試験はこのプロジェクトで行わず、ローカル（`supabase start`）か使い捨てのプロジェクトで行う。

## 検証

以下は実装後に行う検証。外部サービスを使わないテストではGoogle・Geminiをモックにする。

### DB

2026-10-17に以下を実施した（ローカル：全項目、`Meelyze-plus`：適用・読取専用チェック・ロールバックする検証SQL）。手順・結果・未実施事項は [Supabase README](../supabase/README.md#実施結果2026-10-17) を参照する。

- 空のDBへ順番に適用でき、2回目の `db push` で差分が出ないこと。11テーブル・RPC4つ・公開ビュー3つと29＋4種のマスタが仕様に一致すること。
- 解析・確認・本人設定置換がそれぞれ原子的で、途中失敗時に部分保存されないこと。料理の配列順を保存・再取得できること。
- 両回答の不変性、メニュー・料理・項目の外部キー、未知ID・重複・未回答の拒否、明示的な `unknown` の保存。
- 同一メニューの並行送信でも5件上限を守り、同一内容の再送は上限到達後も成功すること。異なる内容は409になること。
- 公開条件の8通り（利用者同意×店員同意×店舗）を検証し、別の公開確認の存在だけで不同意の回答を公開しないこと。
- `service_role` 相当で行ロックとRPCが動き、直接のスナップショット更新は拒否されること。`anon`・`authenticated` のアクセスを拒否すること。
- 本人設定への同時PUTが混合状態を残さず、いずれかの完全な設定になること。登録時同意・所有者はDBから保存し、ゲストは所有者NULL・同意falseを維持すること。
- Supabase実環境でStorageの非公開設定・APIによる削除・SDKのRPCを確認する。通常のPostgreSQLでStorage以外を検証する場合も `anon`・`authenticated`・`service_role` のロールを用意する。

### API・認証・公開範囲

- API一覧とOpenAPI・Pydanticが一致し、未定義フィールド・入力上限・不正型・無効画像を拒否すること。
- 解析用トークンなし・他メニュー・期限切れ、アカウントJWTの署名不正・期限切れ・typ違いを拒否し、2種類を代用できないこと。
- 新規解析のBearerは省略可能だが、無効なら401。本文の所有者・利用者同意は拒否し、登録済みの同意から決めること。
- 登録の同意はtrue／falseとも受理し、欠落・nullを拒否すること。日時・文言バージョンをクライアントに指定させず、平文パスワードを保存・返却しないこと。
- 大文字小文字違いの重複メールは409。メール不存在・パスワード違いは同じ401。登録・ログイン・解析・周辺検索のレート制限は429。
- 確認の直積、両配列の料理集合、10料理・50問・5回の上限を検証する。片側だけの確認も許可し、両方空は拒否すること。
- 公開集計に非公開回答の内容・件数、所有者・menu_id・dish_id・session_id、個別カード・画像・トークン・本人設定が出ないこと。代表料理を安定して選び、AIの票を1件分だけ加えること。
- 履歴の店舗フィルター・ページングでも所有者条件が外れないこと。他人・存在しないメニューは同じ404。未確認・非公開・店舗未選択を本人だけが読めること。
- 履歴の個別回答は本人の当該メニューだけ。画像削除・解析トークン失効後も閲覧できるが、アカウントJWTで回答追加はできないこと。ゲスト履歴を後から自動移管しないこと。
- ログへの機密情報流出がなく、Storage保存後のDB失敗で画像を削除すること。

### 予測

- 根拠の優先順位・重複除去・statusとsourceの整合性。料理名のNFKC・空白除去・小文字化と、表記が異なる料理の分離。
- 回答なしはAIのみ、不明回答のみならAIの分類を維持し、件数・最終日時には不明も含めること。ゼロ除算しないこと。
- 重みが0日1.0・30日0.5・60日0.25となり、APIの計算例と一致すること。同率の優先順と両極の回答の不一致検出。
- 店舗・料理名キー・項目ID・アレルゲン／食事制限の種類を混同せず、公開集計には公開対象だけを使うこと。

### 画面

- ゲストの①→②→⑤、登録の①→②→③→⑤、ログインの①・③→④→⑤。保存済み設定と登録成功メッセージの出し分け。
- ⑤・⑰で29品目・食事制限4種を編集でき、Other・言語切替がないこと。本人の2つのPUTは両方成功するまで遷移せず、片方失敗時は失敗側を再試行すること。
- 複数人の対象は種類ごとの和集合。全項目選択時は1料理33問、2料理66問となり、50問超過時に項目を黙って省略しないこと。
- ⑥→⑧、⑥→⑦→⑧の店舗引継ぎとConfirm／Skip。iOS Safari・Android Chromeで位置情報拒否・店舗なし・撮影／画像選択を確認する。
- ⑨→⑩では送信せずAnalyzeで送信すること。Retake・失敗からの再試行、⑪→⑫→⑬→⑭→⑮→⑪′の往復で余分な解析をしないこと。
- 店員回答4択は初期未選択。未回答は進めず、Unknownは有効回答。⑬→⑭の下書き保持・途中離脱の破棄・二重押し・結果不明後の再送。
- 同意は利用者が③、店員が⑭。保存成功時だけ⑮へ進み、APIの公開判定を表示すること。AIと店員回答を分け、不一致・不明・再確認を示すこと。
- ⑮の再表示、状態喪失時の本人履歴からの復旧、ゲストの直リンクからの案内。公開集計を個別回答として代用しないこと。
- ⑦の公開集計と同店舗の本人履歴、⑯からの全店舗の本人履歴を区別すること。閲覧だけでは履歴を増やさないこと。
- Profile→⑯、Change→⑰、保存→⑯。本人情報は本人だけ、パスワード欄は固定の伏せ字。ログアウト・期限切れで本人のキャッシュとトークンを破棄し、同行者設定を保つこと。
